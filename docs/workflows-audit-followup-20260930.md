# Потоки: подготовленные исправления 4 и 5

Статус: локальная подготовка. Не развёрнуто на проде. Пункты 1 и 2 из прошлого изменения здесь не повторяются.

## 4. Собственные изменения и рекурсия

Новая защита включается отдельно: `WORKFLOWS_PRECISE_LOOP_GUARD=true`. По умолчанию выключена, текущая защита продолжает работать.

- Перед поддерживаемым запросом записи сохраняется намерение в БД. Если журнал недоступен, запрос записи не отправляется.
- Успешный ответ, отказ API и неизвестный результат при обрыве соединения различаются.
- Совпавший ID созданной записи или примечания подтверждает собственное событие. Оно не запускает этот или другой процесс аккаунта.
- Для изменения существующей записи другая версия `updated_at` / `last_modified` проходит как независимое событие. Нет общего запрета всех событий сущности на 15 минут.
- Совпавшее время, отсутствующее время, неподтверждённый ответ, изменение связей и несовпадающее представление полей не считаются доказательством происхождения. Событие сохраняется в разделе «Требуют проверки» без запуска.
- Повторная доставка одного спорного события не создаёт второй элемент проверки. Владелец может перепроверить или оставить его без запуска. Выполнить один раз можно только событие, которое проверка уже признала независимым.
- Проверка принадлежности аккаунту выполняется на сервере. Данные события и снимок сценария зашифрованы. В журнале полей хранятся отпечатки значений, а не открытые данные CRM.

### Ограничения, которые нельзя скрывать

Это консервативная защита, не универсальное определение автора. В опубликованном [формате webhook amoCRM](https://www.amocrm.ru/developers/content/crm_platform/webhooks-format) нет общего гарантированного идентификатора нашего HTTP-запроса. Изменения в одну секунду могут быть неразличимы. Совпавшие значения тоже не доказывают автора.

Проверка инструментирует прямые записи исполнителя в сделки, контакты, компании, покупателей, задачи, примечания и связи. Косвенные изменения от Salesbot, Digital Pipeline, внешних интеграций и отложенного «Распределения» требуют отдельных правил происхождения. Нельзя обещать абсолютную защиту всего аккаунта на основании этого журнала.

Неоднозначные PATCH и связи могут создавать много записей проверки. Ручного принудительного запуска с обходом защиты нет. Перед широким включением нужно измерить их долю на тестовом аккаунте. Для автоматического разбора следующим шагом нужен сверяющий процесс по журналу событий amoCRM, где доступно достаточно доказательств; не авторазрешение по таймеру.

Журнал намерений пока не очищается автоматически: истечение времени не должно превращать неизвестное происхождение в разрешение запуска. Нужны измерение роста, политика хранения и безопасная архивация доказательств. До этого широкий запуск новой защиты не рекомендован. Записи обычных запусков продолжают жить по прежней политике.

### Приёмка перед включением

1. Применить новую миграцию на тестовой базе. Проверить внешние ключи и размер записей на MySQL, локальные тесты используют SQLite.
2. На отдельном тестовом аккаунте включить флаг. Остановить старые исполнители перед переключением, дождаться обработки старых вебхуков, затем запустить исполнители с новой конфигурацией.
3. Проверить создание, PATCH, заметку, привязку, ручное изменение сразу после ноды, две записи в одну секунду, задержанный webhook и повторную доставку. Собственная запись не должна запускать соседний сценарий.
4. Проверить отказ БД до записи, timeout после отправки, повторный запуск исполнителя. Не повторять неизвестный POST вслепую.
5. Измерить долю спорных событий и нагрузку дополнительного GET перед PATCH. Для связей используются версии обеих сущностей до и после запроса, до четырёх дополнительных GET. События вне подтверждённого интервала проходят дальше; при недоступном контрольном чтении остаются спорными. Если спорных событий много, сначала доработать автоматическую сверку, не перекладывать поток проверок на владельца.
6. Прод только после отдельного разрешения. Откат: выключить флаг, обновить конфигурацию и исполнителей; новые таблицы сохранить, не откатывать миграцию с данными.

## 5. Упрощение настройки

- Одна основная форма вместо трёх постоянно открытых колонок.
- Данные и результат открываются отдельными панелями по кнопке. «Переменная» открывает выбор данных для текущего поля.
- Поиск по русским названиям, выбор значения нажатием, понятная подпись источника и пример значения. JSON доступен отдельно в техническом режиме.
- JSON-настройка amoCRM-действий находится в сворачиваемом разделе. Ранее сохранённый JSON-режим остаётся рабочим и открытым.
- Источник целевой сущности можно указать явно: запуск, входящая нода, ID/переменная. Старый автоматический режим сохранён для совместимости.
- Входящая нода не подменяется последним выполненным соседом. Из списка не выбирается первая запись автоматически.
- Под нодами показаны короткие настройки условия, задачи, заметки, задержки и создания сущности.

Это улучшение основного редактора, а не завершённый новый продуктовый слой. Человеческие подписи пока покрывают основные поля. Для неизвестных полей остаются исходные имена; выражения остаются видимыми и редактируемыми. Нужны отдельные пользовательские проверки на типовых задачах.

## Что делать с оставшимися рисками

Это задачи разработки, не обязанность пользователя вручную обходить ошибки.

| Приоритет | Проблема | Следующее изменение | Как проверить |
| --- | --- | --- | --- |
| P0 | Повтор webhook создаёт обычный запуск ещё раз | Единый журнал входящих событий, ключ идемпотентности, уникальность события и точки запуска | Одно событие отправлено 10 раз, одна цепочка действий |
| P0 | Повтор доставки задания исполнителю | Атомарное право на выполнение шага, lease и проверка состояния RUNNING | Два работника одновременно берут задание, запись в CRM одна |
| P0 | Неизвестно, прошёл ли POST после timeout | Состояние «результат неизвестен», сверка результата, запрет слепого повтора | API выполнил создание, соединение оборвалось, дубля нет |
| P1 | Сценарий меняется, пока запуск ждёт | Неизменяемая опубликованная версия и снимок при постановке в очередь | Изменение черновика не меняет уже принятый запуск |

| P2 | Слишком низкий порог входа только у разработчика | Шаблоны типовых задач, подписи по смыслу, простой и расширенный режимы | Новый пользователь собирает типовой сценарий без знания JSON |

Эти строки не реализованы данной правкой. Защита от дублей в новой очереди проверки не означает идемпотентность всех обычных запусков.

## Локальная проверка

- Новые тесты: 16 тестов, 56 утверждений, все прошли. Есть проверки времени, ID созданных записей, связей обеих сущностей, отказа до HTTP, timeout, изоляции владельцев, повторной доставки и сохранения источника сущности.
- Полный набор `tests/Unit/Workflows`: 617 тестов, 612 прошли, 5 завершились ошибками доступа к отсутствующему локальному MySQL. Ошибок утверждений нет. Зависимые тесты: четыре в `RunWorkflowActionTest`, один в `WorkflowAmoCrmLoopGuardTest`.
- JavaScript: 54 теста, все прошли. Сборка интерфейса прошла.
- В локальном браузере на вымышленных данных проверены форма задачи, скрытый JSON-режим, поиск «бюджет», вставка переменной с примером 15000, закрытие выбора и отдельная панель результата. Ошибок в консоли нет.
- Реальные записи в amoCRM, миграция MySQL и прод не выполнялись. Это не заменяет приёмку новой защиты на тестовом amoCRM-аккаунте.
