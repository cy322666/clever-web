# Автотесты событий и нод

Каталог содержит 43 типа запуска и 35 типов нод. Покрытие сверяется с действующими реестрами: новая нода или триггер без примера ломает тест. Синтетические JSON-примеры явно отделены от реальных ответов и исторических запусков. Секреты маскируются при экспорте.

## Ежедневные реальные проверки и Telegram

Включаются только для согласованного технического аккаунта:

```dotenv
WORKFLOW_ACCEPTANCE_ENABLED=true
WORKFLOW_ACCEPTANCE_WORKFLOW_ID=15
WORKFLOW_ACCEPTANCE_DOMAIN=widgetscenario
WORKFLOW_ACCEPTANCE_AMO_ACCOUNT_ID=33098322
WORKFLOW_ACCEPTANCE_TIME=03:00
WORKFLOW_ACCEPTANCE_TIMEZONE=Europe/Kaliningrad
```

Планировщик Laravel запускает `workflows:acceptance` ежедневно в **03:00 по Калининграду**, независимо от часового пояса приложения. Команда запускает отдельный процесс с реальными API-запросами, ждёт завершения и отправляет краткий русский отчёт в общий админский Telegram-чат. Используются единые `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` и необязательный `TELEGRAM_MESSAGE_THREAD_ID`, как для остальных системных уведомлений. Доступ бота к чату нужно проверить до включения расписания.

Первый прогон создаёт одну закрытую QA-сделку, одну QA-задачу и отдельный неактивный между проверками сценарий-приёмник. Следующие прогоны используют их повторно: проверяют реальные чтение, изменение, статусы, теги, связи, изменение/завершение задачи и доставку вебхуков. Контакт только существующий; имя восстанавливается. Перед прогоном все имеющиеся сделки должны быть закрыты, количество сделок/контактов/компаний не должно превышать 10. Создание контактов/компаний запрещено.

Ежедневный режим **не равен полному покрытию всех нод**: повторное создание, копирование, добавление примечаний, неподготовленные сервисы и отсутствующие сущности обозначаются как пропуски, не как успех. Это предотвращает накопление QA-сущностей и примечаний. Рабочие сценарии тестового владельца приостанавливаются на время проверки и восстанавливаются; временная подписка удаляется. Клиентские аккаунты не затрагиваются.

Результаты находятся в приватном каталоге `storage/app/private/workflow-acceptance/`. Telegram содержит итоги, конкретные ошибки и имя файла, без токенов и полного CRM JSON. `state-15.json` — постоянный checkpoint: **не удалять ради повторного запуска**. После незавершённой очистки он блокирует новые изменения до ручного восстановления по `recovery`. Таймаут посылает SIGTERM и оставляет время на очистку; при аварии ОС/сервера восстановление всё равно нужно проверить отдельно.

Ручной повтор именно ежедневного набора (после настройки окружения):

```sh
php artisan workflows:acceptance
```

Команда с отключённым флагом ничего не меняет. Включённый режим не является dry run. Параллельные прогоны блокируются. В Telegram приходит и успешный, и ошибочный результат; пропущенные проверки перечисляются отдельно в JSON. Ошибка доставки Telegram остаётся в JSON/логе и даёт ненулевой код выхода; доставка при недоступном Telegram не гарантируется.

Механизм расписания соответствует [Laravel Scheduler](https://laravel.com/docs/12.x/scheduling); подтверждение приёма уведомления проверяется по ответу [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).

## Локальные контрактные проверки

Из корня проекта:

```sh
php application/vendor/bin/phpunit -c application/phpunit.xml application/tests/Unit/Workflows/Testing application/tests/Unit/Workflows/WorkflowAmoCrmWebhookPayloadNormalizerTest.php application/tests/Unit/Workflows/WorkflowAmoWebhookEventsTest.php --log-junit output/workflow-acceptance-2026-09-19/contract-tests.xml
```

Тесты используют SQLite в памяти, подменённые внешние ответы и запрет случайных HTTP-запросов. Они расположены в существующей Unit suite и запускаются вместе с ней в CI. Реальный прогон намеренно отдельный, не запускается при каждом коммите.

Проверяются нормализация событий, form-urlencoded, пакетные payload, смешанные компании/контакты, порядок/типы данных, условия/выражения, запросы нод, реальные обработчики с подменой HTTP, ошибки 403 без повторов, защита от создания запрещённых сущностей и очистка секретов. Неподдерживаемые ноды проверяются на явную ошибку; успешное действие для них не заявляется.

## Только чтение подключённого аккаунта

Из `application/`, в окружении с доступом к подключению:

```sh
php scripts/workflow-acceptance.php --workflow=15 --expected-domain=widgetscenario --report=/private/report/read-only.json --read-only
```

Только GET/HEAD на домен выбранного amoCRM. Сценарии не приостанавливаются, данные CRM не изменяются. Экспортируется до 60 прошлых запусков только владельца выбранного сценария. Как и обычная работа подключения, может потребоваться обновление OAuth-токена.

## Реальный прогон с изменениями

```sh
php scripts/workflow-acceptance.php --workflow=15 --expected-domain=widgetscenario --report=/private/report/live.json --execute
```

Только для явно выбранного технического аккаунта. Требует разрешения на следующий набор действий:

- Приостановить активные сценарии этого владельца на время прогона и восстановить их в `finally`.
- Закрыть все открытые сделки аккаунта в 143; создать две уже закрытые QA-сделки для тестов создания/копирования.
- Временно изменить имя существующего контакта, затем восстановить; создать примечания, привязать/отвязать контакт только к QA-сделке.
- Создать тестовую задачу и завершить её.
- Создать отдельный QA-сценарий приёма хуков и временную подписку amoCRM, после прогона удалить эту подписку и архивировать QA-сценарий. История сохраняется.

Новые контакты, компании и покупатели запрещены на уровне исходящих HTTP-запросов, включая вложенное создание. Удаление существующих сущностей, отправки Telegram, SalesBot и произвольные внешние изменения не выполняются. Изменяющие запросы ограничены явным списком; новые сделки создаются по одной сразу в 142/143. Существующие незавершённые запуски блокируют старт.

JSON обновляется после каждого кейса и содержит `recovery` с ID сценариев, задач и исходными полями контакта. При аварийном завершении процесса/сервера `finally` может не выполниться: проверьте этот checkpoint перед повторным запуском, восстановите перечисленные поля/активацию и удалите только временную подписку QA. Не удаляйте рабочие подписки. Обычные ошибки тестов обрабатываются с выполнением cleanup.

Ограничение реального покрытия: создание контакта запрещено пользователем; компаний/покупателей/части справочников может не быть; сообщения, SalesBot и Digital Pipeline требуют подготовленного отдельного окружения. Такие кейсы обозначаются как пропущенные, а не успешные. Приём webhook в QA-потоке и нормализация проверяют доставку/данные, но не заменяют все проверки диспетчеризации каждого вида триггера.

## Итоговый файл JSON

```sh
php application/scripts/export-workflow-acceptance.php --live=/private/report/live.json --junit=output/workflow-acceptance-2026-09-19/contract-tests.xml --output=output/workflow-acceptance-2026-09-19/events-and-node-results.json
```

Можно передать отчёт `read-only.json` вместо `live.json`. Поля `provenance`, `coverage`, `live_limitation` объясняют источник и границы проверки. `expected_result` — пример, `live_executions[].result` — фактический результат сервера. `historical_runs` — сохранённая ранее история, не текущий тест. Полный исходный JSON оставлен для анализа интерфейса; технические поля не удалены, кроме секретов.

Отдельное явно запрошенное закрытие существующих сделок выполняет `scripts/workflow-acceptance-close-leads.php` с теми же workflow/domain/report/execute аргументами. Он разрешает только PATCH конкретной сделки с единственным полем `status_id: 143`, без создания данных и паузы сценариев. Его результат можно приложить к экспорту параметром `--closure=/private/report/closure.json`.

Форматы сверялись с официальными [описанием вебхуков](https://www.amocrm.ru/developers/content/crm_platform/webhooks-format), [API подписок](https://www.amocrm.ru/developers/content/crm_platform/webhooks-api) и [API сделок](https://www.amocrm.ru/developers/content/crm_platform/leads-api). Факт доставки и доступность конкретного метода проверяются отдельно на выбранном аккаунте.
