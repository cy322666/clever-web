# Отраслевое решение «Клиники и салоны»

Дата: 17 сентября 2026 года. Версия: 0.1 — спецификация по обсуждению и четырём скриншотам пользователя.

Статус: состав решения зафиксирован для дальнейшей разработки. В живом аккаунте amoCRM ничего не настроено, установочный пакет не создан. Название продукта рабочее.

## 1. Модель

- Одно общее решение для ветеринарии, бьюти-сетей, медицинских услуг и массажных салонов.
- Основная воронка: одна сделка соответствует одной записи. На ранних этапах запись ещё может не быть оформлена; это не основание создавать вторую сделку при её появлении.
- Новая самостоятельная запись — отдельная сделка; перенос той же записи — обновление существующей сделки. При реализации сопоставлять по идентификаторам конкретной системы, не только по телефону клиента.
- Реактивация: работа по возврату клиента. Источники — отмены, неявки, давно не посещавшие клиенты и вручную выбранные сегменты.
- Абонементы: одна сделка соответствует одному абонементу.
- Предложения по механике реактивации: сохранять историю исходной записи, исключать повторные активные обращения в рамках одной кампании, связывать результат с записью в основной. Создание или перенос сделки и точные правила дублей ещё не утверждены.

## 2. Воронки и этапы

### Основная

1. Новый лид
2. Взят в работу
3. Контакт установлен
4. Квалифицирован
5. Клиент записан
6. Запись подтверждена
7. Клиент пришел
8. Успешно реализовано — успешный финальный статус
9. Закрыто и не реализовано — неуспешный финальный статус

Названия сохранены со скриншота, в том числе «Клиент пришел».

### Реактивация

1. Новый лид
2. Взят в работу
3. Недозвонились
4. Квалифицирован
5. Отправлен в основную — успешный финальный статус
6. Закрыто и не реализовано — неуспешный финальный статус

Источник этапов — скриншот воронки «Исходящая». Рабочее название в продукте — «Реактивация», согласно обсуждению; четвёртая воронка не добавляется.

### Абонементы

1. Абонемент куплен
2. Начал посещать
3. Ждет допродажи
4. Абонемент куплен — успешный финальный статус (УР)
5. Абонемент не куплен — неуспешный финальный статус (ЗИН)

Первый и успешный финальный этапы намеренно сохранены с одинаковым названием по требованию пользователя. При настройке различать их по идентификаторам и типу статуса. Значение успешного финала (допродажа, продление или другое событие) ещё требуется определить для автоматизации.

## 3. Основная вкладка сделки

Состав и порядок взяты со скриншота с указанными пользователем исключениями. Тип «Интересующие услуги» задан пользователем; прочие типы ниже — предлагаемые, поскольку скриншот не раскрывает все настройки полей.

| Поле | Тип / настройка |
| --- | --- |
| Ответственный | Стандартное поле amoCRM; не создавать дубль |
| Бюджет | Стандартное поле amoCRM; не создавать дубль |
| Тип клиента | Список; предлагаемые значения: Первичный, Повторный |
| Интересующие услуги | Текстовое поле, не список и не мультисписок |
| Услуга | Текст; заполнение из выбранной системы записей при наличии данных |
| Дата и время записи | Дата и время |
| Комментарий | Многострочный текст |
| Филиал | Текст, рабочий вариант для совместимости с интеграциями |
| Специалист/Врач | Текст; заполнение из выбранной системы записей при наличии данных |
| Рекламный источник | Список; значения пока не предоставлены |
| Причина отказа | Список; значения пока не предоставлены |
| Подробная причина отказа | Многострочный текст |

Не включать: `COMMENTS`, `Source phone`, `PROMOKOD`, «Причина отмен», «Источник захода», «Название базы».

«Комментарий» и «Подробная причина отказа» сохраняются. Они не относятся к исключённому `COMMENTS`.

В универсальном продукте используются названия «Услуга» и «Специалист/Врач», чтобы поля подходили YClients, SQNS и Ветменеджеру.

## 4. Отдельная вкладка системы записей

Служебные поля вынести в отдельную вкладку/группу. На скриншоте она называется «YC». Рабочее предложение для продукта — вкладка по названию выбранной системы; при нескольких системах не смешивать их идентификаторы.

| Поле | Предлагаемый тип |
| --- | --- |
| ID записи | Текст, чтобы сохранять строковые идентификаторы без преобразования |
| ID компании | Текст; идентификатор компании в системе записей, не ID компании amoCRM |
| Создатель записи | Текст |
| Отдел создателя | Текст |
| Роль создателя | Текст |
| Дата создания записи | Дата и время |
| Источник записи | Текст |

Поля заполняет интеграция. Ручную обязательность не устанавливать. Наличие полного набора данных в YClients, SQNS и Ветменеджере нужно проверить отдельно; если источник не отдаёт значение, не подставлять вымышленное.

## 5. Обязательность полей — предлагаемый стандарт

Пользователь потребовал настроить обязательность. Конкретные этапы не указаны; ниже рабочая матрица, которую следует использовать как предложение при реализации.

| Воронка | Переходы, при которых поля обязательны | Поля |
| --- | --- | --- |
| Основная | Квалифицирован, Клиент записан, Запись подтверждена, Клиент пришел, Успешно реализовано | Тип клиента; Интересующие услуги |
| Основная | Клиент записан, Запись подтверждена, Клиент пришел, Успешно реализовано | Дата и время записи |
| Основная, если используется несколько филиалов | Клиент записан, Запись подтверждена, Клиент пришел, Успешно реализовано | Филиал |
| Реактивация | Квалифицирован, Отправлен в основную | Тип клиента; Интересующие услуги |
| Основная и Реактивация | Закрыто и не реализовано | Причина отказа |
| Абонементы | Абонемент не куплен | Причина отказа |

Остальные поля пока необязательны. «Подробная причина отказа» дополняет причину без требования писать текст при каждом отказе. Дату отдельного посещения не делать обязательной для абонемента. На первом этапе не вводить обязательность, которая мешает принять входящее обращение.

Технически обязательность задаётся по парам «воронка + этап» через `required_statuses`. Перечислять все необходимые этапы явно, включая переход с пропуском промежуточных стадий. После реализации отдельно проверить ручное изменение этапа и переходы через каждую интеграцию; наличие настройки не заменяет проверку поведения API.

## 6. Автозадача

Подтверждённое требование: новая сделка на первом этапе → задача «Взять в работу».

Рабочее предложение:

- Применять ко всем трём воронкам: первому «Новый лид» в Основной и Реактивации, первому «Абонемент куплен» в Абонементах.
- Исполнитель — ответственный за сделку. Если включено распределение, учитывать итогового ответственного.
- Срок выполнения — 30 минут.
- Не создавать повторную задачу из-за повторной доставки одного события или повторного сохранения сделки.
- Условие — создание сделки на первом этапе. Простое возвращение существующей сделки на первый этап не считается новым созданием.
- Демонстрационные сделки исключить из рабочих автозадач.

Использовать штатное действие Digital Pipeline amoCRM «Создать задачу». В техническом аккаунте отраслевого решения для каждой воронки настроить событие «создание сделки» на первом этапе, текст «Взять в работу», срок 30 минут, исполнитель — ответственный за сделку. Сторонний виджет для этой задачи не устанавливать.

Публичный API amoCRM не документирует создание нативных правил Digital Pipeline. Поэтому перенос правила из технического аккаунта в новые аккаунты отраслевого решения нужно подтвердить с командой интеграций amoCRM до модерации; подменять его недокументированным запросом нельзя.

## 7. Выбор интеграций при установке

Все варианты — интеграции платформы пользователя:

- YClients
- SQNS
- Ветменеджер
- Распределение
- MAX
- Telegram
- WhatsApp
- ВКонтакте
- Авито
- Instagram Direct
- Тильда

Пользователь выбирает нужные варианты в мастере установки. Для каждого мессенджера используется отдельный переключатель; все варианты выключены до выбора. Допускается несколько систем записей и несколько каналов. Невыбранные интеграции не устанавливать и не подключать.

Предлагаемая последовательность мастера:

1. Настройки работы: одна точка/сеть; показать три создаваемые воронки и штатную задачу «Взять в работу» со сроком 30 минут.
2. Выбор интеграций и конкретных мессенджеров; показать стоимость и условия выбранного состава.
3. Проверка итогового состава и подтверждение установки; после установки — краткая инструкция, подключение внешних аккаунтов, авторизация и сопоставление данных.

Выбор интеграции, установка публичного виджета и успешное подключение внешнего аккаунта — разные состояния. Показывать их раздельно. Для незавершённого подключения сохранять состояние «Требуется подключение».

## 8. Ограничения официального формата amoCRM

Проверено по документации 17 сентября 2026 года:

- Отраслевое решение устанавливается при создании нового аккаунта; штатная установка в существующий аккаунт этим форматом не предусмотрена.
- Устанавливаемые виджеты и интеграции должны быть публичными. Наличие модуля в коде платформы не доказывает публикацию в amoМаркет.
- Для пользователей отраслевого решения интеграции должны предоставлять 14 дней тестирования. Это отдельное условие для данного канала установки.
- Мастер содержит минимум два шага настроек. Во время мастера нельзя требовать переходить в другие окна за логинами, паролями или API-ключами: выбор выполняется в мастере, авторизацию внешнего сервиса предлагается завершать после него.
- После мастера обязательна инструкция; в каждой создаваемой воронке нужен демонстрационный пример по правилам amoCRM.
- До разработки требуется согласование идеи с amoCRM; заявку сопровождают описанием и видео эталонного решения.

## 9. Что ещё нужно определить

- Публичные коды виджетов MAX, Telegram, WhatsApp, ВКонтакте, Авито и Instagram Direct.
- Словари «Рекламный источник» и «Причина отказа»; окончательные типы остальных полей.
- Подтверждение команды интеграций amoCRM, что штатная автозадача переносится из технического аккаунта в новый аккаунт отраслевого решения.
- Какое событие переводит абонемент в успешный финал и как это связано с продлением.
- Порог «давно не ходил», обработка отмен/неявок, создание или перенос реактивации и действия при «Отправлен в основную».
- Доступность публичных виджетов, их коды, цены и 14-дневный тест для отраслевого решения.

Эти пункты не мешают зафиксировать структуру сейчас; автоматизацию неизвестных бизнес-правил не считать реализованной.

## 10. Проверка будущей реализации

- Созданы ровно три воронки с указанными этапами; одинаково названные этапы абонемента различаются по ID и назначению.
- В основной вкладке сохранены все нужные поля, исключённые отсутствуют; «Интересующие услуги» имеет тип «Текст».
- Служебные поля находятся на отдельной вкладке интеграции и не требуют ручного заполнения.
- Обязательность проверена при последовательных переходах и пропуске этапов, отдельно для каждой воронки.
- Новая сделка в первом этапе получает одну задачу; срок и исполнитель соответствуют настройке.
- Устанавливаются только выбранные интеграции и мессенджеры; доступно подключение выбранного состава после мастера.
- Повторный вебхук не создаёт повторную запись или задачу; перенос существующей записи не создаёт вторую сделку.
- Рабочая запись, реактивация и абонемент различаются при подсчёте посещений и выручки.
