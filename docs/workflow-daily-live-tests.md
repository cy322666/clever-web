# Ежедневные реальные проверки amoCRM

Расписание: 03:00 Europe/Kaliningrad. Только технический аккаунт widgetscenario.amocrm.ru (33098322), подключение через сценарий 15. По умолчанию отключено.

Настройки окружения: WORKFLOW_ACCEPTANCE_ENABLED=true, WORKFLOW_ACCEPTANCE_WORKFLOW_ID=15, WORKFLOW_ACCEPTANCE_DOMAIN=widgetscenario, WORKFLOW_ACCEPTANCE_AMO_ACCOUNT_ID=33098322. Время и пояс задаются WORKFLOW_ACCEPTANCE_TIME/WORKFLOW_ACCEPTANCE_TIMEZONE.

Telegram: используются единые TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID и необязательный TELEGRAM_MESSAGE_THREAD_ID. Отчёты приходят в общий админский чат вместе с остальными системными уведомлениями. Полный CRM JSON в Telegram не отправляется.

Команда `php artisan workflows:acceptance` выполняет тот же набор вручную. Это реальные действия, не dry run. Сначала запускайте без расписания и проверяйте cleanup отчёта, затем включайте ежедневный режим.

На первом прогоне создаются одна закрытая QA-сделка, одна задача и отдельный QA-сценарий-приёмник. Затем они используются повторно. Проверяются чтение, изменение сделки/контакта, статусы 142/143, теги, связи, изменение/завершение задачи и получение webhook с выполнением шага. Новые контакты запрещены; для проверок автоматически готовится постоянная QA-компания в пределах лимита десяти компаний. Контакт восстанавливается, QA-задача закрывается, временная подписка удаляется, прежняя активация сценариев возвращается. Сущностей каждого типа должно быть не больше десяти.

Перед каждым регулярным прогоном открытые сделки переводятся в 143 только в явно разрешённом техническом аккаунте widgetscenario (33098322), сценарий 15. Проверяются технический тип аккаунта, домен, ID amoCRM, владелец подключения и checkpoint; затем приостанавливаются сценарии. Исходные статусы и точное намерение каждого изменения сохраняются до PATCH, ответ проверяется повторным чтением. Разрешено менять только `status_id` конкретной сделки, не остальные поля. Уже закрытые сделки не меняются. Новые или исчезнувшие во время подготовки сделки, превышение лимита и неподтверждённое изменение останавливают прогон. В других аккаунтах старое требование закрытых сделок сохраняется. Подготовка отражается в `preparation.close_existing_leads`, но не выдаётся за успешную проверку ноды.

Повторное создание/копирование сделок и добавление примечаний пропускаются, чтобы ежедневный тест не засорял CRM. Неподготовленные сервисы и отсутствующие сущности не считаются проверенными. Отчёт честно различает passed/failed/skipped.

Недостающие данные для чтения готовятся автоматически: постоянные QA-компания и покупатель, отдельный обычный список с элементом и полем, примечания и одна тестовая покупка QA-покупателя; доступные поля и сегменты переиспользуются либо создаются один раз. Идентификаторы сохраняются в `read_fixtures` checkpoint. Подготовка через API учитывается отдельно от проверок нод: создание тестовых данных не выдаётся за успешное выполнение ноды. Перед POST сохраняется точное намерение; неизвестный результат или сбой сохранения блокирует повтор, чтобы не создать дубликаты. Режим покупателей не переключается: в режиме «Сегменты» проверки этапов помечаются неприменимыми.

Приватные отчёты: storage/app/private/workflow-acceptance/*.json. Постоянный checkpoint: state-15.json. При phase=running/recovery_required следующий прогон блокируется. Не удаляйте checkpoint ради повтора: сначала восстановите данные из recovery, проверьте аккаунт/активацию/QA-подписку и только затем вручную разрешите ready. SIGTERM пытается выполнить finally; авария сервера может потребовать ручного восстановления.

Подписка QA создаётся одним запросом. Её появление, включённость и полный набор событий проверяются повторными чтениями с ограниченным сроком ожидания. Это не повтор бизнес-действий сценария. При очистке удаляется только точный адрес QA-приёмника, даже если он ещё не появился в списке; затем проверяется устойчивое отсутствие подписки. Неподтверждённая очистка блокирует следующий прогон. В отчёте сохраняются этапы проверки, ID подписки и недостающие события без секретного URL. После общего таймаута дочернему процессу даётся до 180 секунд на восстановление аккаунта.

Зелёный отчёт требует реально выполненных проверок и успешного восстановления. Ошибки/пропуски видны в Telegram; технические подробности сохраняются только на сервере. При недоступном Telegram доставка не гарантируется, ошибка записывается в отчёт и лог. Планировщик не зависит от ноутбука/Codex.

Документация: https://laravel.com/docs/12.x/scheduling, https://core.telegram.org/bots/api#sendmessage и https://new.amocrm.ru/developers/content/crm_platform/webhooks-api.
